# Scout: v0.7.1 - Playlist artwork management

Generated by scouting the repository ahead of implementation. See
`Roadmap to v0.7.md#v071---playlist-artwork-management` for the full spec;
an implementing agent should still run `python3 tools/agent_context.py
v0.7.1` first.

## Goal

Let a user recognize and personalize playlists visually: select, preview,
upload, retry, replace, and remove playlist artwork, with every playlist
surface converging on the server-confirmed image afterward.

## Current state (confirmed by inspection)

- **`ArtworkResolver` is read-only.** `lib/domain/media/ArtworkResolver.dart:17-25`
  is a single method, `imageUrl(MediaImage, {maxWidth, maxHeight}) -> Uri?`.
  No mutation capability anywhere in the contract. `JellyfinArtworkResolver`
  (`lib/infrastructure/jellyfin/media/JellyfinArtworkResolver.dart:19-53`)
  only builds GET URLs against `/Items/{id}/Images/{type}`; it has no
  upload/delete counterpart.
- **No image-picking, cropping, or upload dependency exists.** `pubspec.yaml`
  has no `image_picker`, `file_picker`, or `image_cropper` entries (checked
  `pubspec.yaml:40-78`) — only `dio` (46), `cached_network_image` (56), and
  `flutter_cache_manager` (59) for the read-side artwork cache (ADR-0010).
  Picking/cropping/upload is genuinely new dependency + domain work.
- **`PlaylistRepository` has no artwork methods.** The contract
  (`lib/domain/media/PlaylistRepository.dart:14-91`) covers `playlists`,
  `tracks`, `addTracks`, `create`, `rename`, `delete`, `removeEntries`,
  `moveEntry` — nothing image-related. `replaceArtwork`/`removeArtwork` (or
  similar) would be new contract members, implemented by both
  `JellyfinPlaylistRepository` (remote) and `CachedPlaylistRepository`
  (pass-through, per its own "Writes" comment at
  `lib/infrastructure/media/CachedPlaylistRepository.dart:203-216` — a
  mutation is never served offline, and the cache is not invalidated inline;
  the caller re-reads instead).
- **`jellyfin_media_api.dart` has no image upload/delete endpoint.** Only
  `addPlaylistItems` (451), `createPlaylist` (477), `renamePlaylist` (502)
  exist for playlist writes; Jellyfin's real endpoints
  (`POST/DELETE /Items/{id}/Images/{type}`) are unimplemented here.
- **The existing mutate-then-refresh pattern to follow is rename.**
  `renamePlaylist()` (`lib/features/music/presentation/widgets/playlist_actions.dart:90-111`)
  is a free function over `getIt<PlaylistRepository>()` that calls the repo,
  shows a snackbar, and returns whether the server accepted it. Its caller,
  `PlaylistDetailPage._rename` (`lib/features/music/presentation/detail/PlaylistDetailPage.dart:139-142`),
  then calls `context.read<PlaylistDetailCubit>().retry()` to reload. This
  same two-step (mutate via free function → cubit `retry()`/`reload()`) is
  the shape an artwork-change action should follow.
- **`PlaylistDetailCubit.retry()` re-fetches via `MediaMetadataRepository.item(id)`**
  (`lib/features/music/presentation/detail/media_detail_cubit.dart:115-131`),
  backed by `CachedMediaMetadataRepository.item()`
  (`lib/infrastructure/media/CachedMediaMetadataRepository.dart:39-47`),
  which re-fetches from Jellyfin and calls `_cache.saveItem(value)` on
  success. **This means the playlist-detail header and the metadata cache
  self-refresh for free once the server has a new image tag** — no new
  cache-invalidation plumbing needed there, just triggering the existing
  `retry()`.
- **Playlist rows do NOT self-refresh.** `PlaylistsCubit`
  (`lib/features/music/presentation/library/music_collection_cubits.dart:216-234`)
  fetches its own page via `PlaylistRepository.playlists()`, cached under
  `MediaCollectionKey.playlists` (`lib/infrastructure/persistence/media/MediaCollectionKey.dart:33`)
  in `CachedPlaylistRepository.playlists` (`lib/infrastructure/media/CachedPlaylistRepository.dart:59-80`).
  This list is a separate read path from the detail header and is not
  updated by a rename or (would not be by) an artwork change unless the
  screen explicitly reloads it.
- **"Home entries" are a third, independently-stale surface.** Playlists
  played as a playlist context are snapshotted into `ListeningContext`
  (`lib/domain/media/ListeningContext.dart:27-40`, `image` on line ~40-ish
  per its doc comment) and rendered by `RecentlyPlayedCubit`
  (`lib/features/home/presentation/RecentlyPlayedCubit.dart:59`). These
  snapshots are taken from the queue at play time and are not tied to
  `PlaylistRepository` reads at all — an artwork change will not reach them
  through any existing refresh call.
- **`DownloadedCollection.image` is captured once and never refreshed.**
  `DownloadedCollection` (`lib/domain/downloads/DownloadedCollection.dart:27-65`)
  says in its own doc comment (lines 18-21) that it is "refreshed whenever
  it is opened online" — but inspection shows this is **not actually true
  for identity (name/image)** today. `DownloadsCubit.downloadPlaylist`
  (`lib/app/downloads/DownloadsCubit.dart:381-424`) calls
  `_rememberCollection(DownloadedCollection(owner: ..., name:
  playlist.name, image: playlist.image))` only once, at download time.
  `DownloadsCubit.reconcilePlaylist` (`lib/app/downloads/DownloadsCubit.dart:458-515`)
  and `ReconcileDownloadedCollection`
  (`lib/features/music/presentation/widgets/reconcile_downloaded_collection.dart`)
  only reconcile *membership* (which tracks are present/`serverGone`), never
  call `_rememberCollection` again. **This is a genuine, pre-existing gap,
  not something v0.7.1 breaks** — but the spec explicitly requires closing
  it for artwork ("downloaded collection identity" refresh), so
  `_rememberCollection` needs a new call site fired after a confirmed
  artwork change (and arguably after rename too, though that's out of
  scope here — flag but don't fix rename's gap unless trivial).
- **No selection/upload progress/retry UI state exists** (parallel to
  v0.7.0's finding that no selection-mode state existed): a repo-wide check
  for `uploadImage`/`imageUpload`/`ImageType`/crop found nothing beyond the
  grep above — this is new presentation state, not an extension.

## Suggested shape (not prescriptive)

- New `PlaylistRepository` methods, e.g. `replaceArtwork(MediaId, ImageBytes)`
  and `removeArtwork(MediaId)`, returning `Result<void>` (or `Result<MediaImage>`
  if the new tag should come back directly rather than via a re-read) —
  decide against the rename precedent (`Result<void>`, caller reloads).
- `JellyfinPlaylistRepository` gains the actual upload/delete call against
  `jellyfin_media_api.dart` (new `uploadPlaylistImage`/`deletePlaylistImage`
  methods, POST/DELETE `/Items/{id}/Images/Primary`), with Jellyfin's format
  and size bounds validated client-side before the request.
  `CachedPlaylistRepository` passes through unchanged, consistent with its
  documented no-offline-write, no-inline-invalidation stance.
- A picking abstraction behind the same domain contract per platform
  (Android document picking, Windows file picking, iOS unchanged) — likely
  a new small domain interface (e.g. `ImagePicker`/`ArtworkSource`) so
  presentation doesn't depend on a picker plugin directly, matching how
  `ArtworkResolver` already isolates image-URL concerns from Jellyfin DTOs.
- Presentation: a new action (parallel to `renamePlaylist()` in
  `playlist_actions.dart`) that picks → previews/crops → uploads with
  progress/retry → on success calls `PlaylistDetailCubit.retry()` (free,
  per above), reloads `PlaylistsCubit`, and calls a new
  `DownloadsCubit` method to re-remember the collection's identity if
  downloaded. Failure/offline must leave the last confirmed `MediaImage`
  in place — never write a locally-picked image into anything that other
  code paths (rows, Home, downloads) treat as server-confirmed.

## Touchpoints to inspect further

- `lib/infrastructure/jellyfin/media/jellyfin_media_api.dart` — where to add
  the actual HTTP image upload/delete calls; check how `dio` is configured
  for multipart/binary bodies elsewhere (playback or none — may be new).
- `lib/app/downloads/DownloadsCubit.dart:733` `_rememberCollection` — the
  right hook to update `DownloadedCollection.image` post-artwork-change.
- `lib/features/music/presentation/widgets/playlist_actions.dart` — where
  the new artwork action likely lives alongside `renamePlaylist`/
  `deletePlaylist`.
- `lib/features/music/presentation/detail/PlaylistDetailPage.dart:88-142` —
  header rendering and the rename call site to mirror.
- Platform picker plugin choice/config for Android document picking vs.
  Windows file picking vs. iOS — check `android/`, `windows/` platform
  folders for any existing file-access permission setup to extend.
- `lib/domain/media/MediaImage.dart` — confirm `tag` semantics are
  sufficient to represent "pending, unconfirmed" vs. "server-confirmed"
  artwork, or whether a new domain type is needed to keep the two from
  being confused (spec explicitly warns against this).

## Non-goals (per spec)

Smart playlist rules/preview (v0.7.2), smart playlist publication/refresh
(v0.7.3), and playlist-system hardening (v0.7.4) are all out of scope here.
Collaborative/cross-user playlist editing remains out of scope for the whole
v0.7.x arc. Album/artist artwork management is not part of this spec — only
playlist artwork.

## Likely ADR

Two durable decisions worth flagging for the next free ADR number
(0049 at time of scouting; re-check `docs/adr/` before implementation
since sibling versions scouted in this batch may also claim one):

1. **Pending-vs-confirmed artwork state contract** — the spec's explicit
   requirement that "pending artwork must never masquerade as a
   server-confirmed change" is a real design decision (how a picked-but-
   not-yet-uploaded, or uploaded-but-offline-unconfirmed, image is
   represented and kept out of `MediaImage`/cache paths that assume
   server-confirmed state).
2. **`DownloadedCollection` identity refresh trigger** — deciding whether
   identity refresh (name/image) rides along on every reconcile (broadening
   scope beyond artwork) or stays a narrow, explicit call fired only after
   a confirmed artwork/rename mutation, given today's real gap found above.
