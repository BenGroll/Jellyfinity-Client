# Scout: v0.8.0 - Durable background download execution

Generated by scouting the repository ahead of implementation. This is a
starting brief, not a replacement for `Roadmap to v0.8.md` or `AGENTS.md` —
an implementing agent should still run
`python3 tools/agent_context.py v0.8.0` first.

## Goal

Make queued music downloads resumable application work rather than a
foreground-screen activity: survive backgrounding and process/device
restart, and either finish or clearly explain what it is waiting for.

## Current state (confirmed by inspection)

- **The queue/scheduler is a `Cubit`, not a platform seam.**
  `lib/app/downloads/DownloadsCubit.dart:23-58` documents itself as "the
  worker that moves them along" and states outright at line 56:
  "Enforcement is foreground only, the same limitation as the foreground
  download engine (ADR-0020, ADR-0022)." All ordering, retry, and network
  gating logic lives in this app-layer, in-memory Cubit — there is no
  scheduler contract for the domain layer to implement per platform.
- **`DownloadEngine` (`lib/domain/downloads/DownloadEngine.dart:48-77`)
  is a pure byte-transfer seam**, not a job scheduler: `fetch`, `abort`,
  `discard`, `locate`, `partialByteCount`. It says nothing about job
  ownership, retry policy, or being invoked by a platform trigger.
- **`HttpDownloadEngine` is explicitly the ADR-0020 foreground-only
  placeholder**, not one of several platform variants. Its doc comment
  (`lib/infrastructure/downloads/HttpDownloadEngine.dart:14-31`) says a
  background-transfer dependency may only be adopted "after an
  Android+iOS resume/cancellation proof of behavior" and that this class
  is "a documented foreground-only implementation" until then — i.e. the
  codebase already names the exact tradeoff v0.8.0 is meant to close.
  There is only one `DownloadEngine` implementation (`rg` found no
  Android/Windows/iOS-specific engine).
- **Restart recovery today is in-process cold-start recovery only.**
  `DownloadsCubit.restore()` (`lib/app/downloads/DownloadsCubit.dart:186-235`)
  resets any record left `DownloadState.downloading` or
  `waitingForNetwork` back to `queued` and re-reads
  `_engine.partialByteCount`/`_engine.locate` to repair drift — but its
  own doc comment says "there is no transfer running in a fresh process."
  It only runs when the Cubit is constructed, i.e. on a live Flutter
  process start, never from a platform-scheduler wakeup. It does not
  revalidate auth, free space, or the remote source before resuming — it
  just re-queues and lets the normal pump run.
- **No retry/backoff/attempt state exists.** `DownloadState`
  (`lib/domain/downloads/download_state.dart:8-41`) has exactly `queued`,
  `downloading`, `paused`, `waitingForNetwork`, `completed`, `failed` —
  no `retrying` state, and `isRetryable` (line 40) just means "show a
  retry button." A repo-wide search for retry-count/backoff fields on
  `TrackDownload` (`lib/domain/downloads/TrackDownload.dart:21-212`)
  found none — `receivedBytes`/`totalBytes`/`failureReason`/`serverGone`
  are the only progress/outcome fields persisted. Retrying today is
  purely user-initiated (`DownloadsCubit` retry methods around lines
  647-684), not automatic.
- **`DownloadStore`/`DriftDownloadStore` persist records, owners,
  playlist snapshots, and collection identity, but no job/lease/claim
  table.** `lib/domain/downloads/DownloadStore.dart:22-139` is the full
  contract; `lib/infrastructure/downloads/DriftDownloadStore.dart:41` is
  the only implementation and persists exactly those fields — nothing
  about which process/device claimed a job, an attempt counter, or a
  policy snapshot (e.g. was this queued under Wi-Fi-only).
- **`DownloadFailureReason`** already includes `unauthorized`,
  `insufficientStorage`, `network`, `storage`, `unavailable`, `unknown`
  (`lib/domain/downloads/download_state.dart:48-78`), so the vocabulary
  for "why a resume can't proceed" partly exists — but nothing calls
  these proactively on resume today; `unauthorized` is only produced
  reactively from a failed request. `SessionCubit` has a reactive
  unauthorized handler at `lib/app/session/SessionCubit.dart:96` ("drops
  the session") that a resume-time revalidation step would need to call
  into or mirror.
- **Free-space check exists and already branches per platform inside one
  class** — `DiskSpaceStorageProbe`
  (`lib/infrastructure/downloads/DiskSpaceStorageProbe.dart:18-49`)
  checks `defaultTargetPlatform == TargetPlatform.windows` (line 33) and
  falls back to `disk_space_plus` otherwise (line 41), both inside a
  single `@LazySingleton(as: DownloadStorageProbe)` class. This is
  advisory-only today (`DownloadStorageProbe.dart:1-38`): a warning, not
  a resume-time gate.
- **No platform background-work dependency in `pubspec.yaml`.** No
  `workmanager`, `background_fetch`, `android_alarm_manager`, or similar
  is present; `audio_service: ^0.18.19` plus `audio_service_win`
  (`pubspec.yaml:66,77`) is the one existing example of a package that
  already gives Jellyfinity a cross-platform background-capable seam
  (for playback, not downloads).
- **No filesystem platform-split convention exists in `lib/`.** Neither
  `_android`/`_windows` folder suffixes nor per-platform filenames were
  found. The actual precedent for platform divergence is (a) inline
  `Platform.isX`/`defaultTargetPlatform` branching inside one class, as
  in `DiskSpaceStorageProbe` above and
  `lib/app/platform/RemotePlaybackBackgroundService.dart:7,13`
  (`if (!Platform.isAndroid) return;`), and (b) a dedicated ADR per
  platform behavior — `docs/adr/ADR-0041-windows-connected-playback.md`,
  `ADR-0042-android-connected-playback.md`,
  `ADR-0043-android-tv-and-fire-tv-connected-playback.md`, and
  `ADR-0046-android-background-connected-playback.md` each cover one
  platform's service behavior as its own decision record rather than a
  directory split.

## Suggested shape (not prescriptive)

- Keep `DownloadEngine` as the byte-transfer seam, but introduce a
  separate platform-neutral scheduler contract (domain layer) that owns
  *when* a job runs — queued/waiting/running/paused/retrying/completed/
  terminal — with Android and Windows implementations plus an iOS-safe
  one that makes no unlimited-background-time promise, following the
  inline-`Platform.isX`-branch-or-dedicated-ADR precedent above rather
  than inventing a new folder convention.
- Extend the persisted record (`TrackDownload`/`DriftDownloadStore`) with
  whatever the scheduler needs to survive restart: attempt/retry count,
  last-attempt timestamp, a claim/owner-process marker if concurrent
  schedulers are possible, and the policy snapshot a job was queued
  under.
- Add an explicit resume-revalidation step (auth, network policy, free
  space, remote source, partial-file integrity) that runs whenever a job
  is picked up — not just at Cubit construction — and make
  `DownloadsCubit.restore()` a caller of it rather than duplicating the
  logic.
- Add a `retrying` (and any other terminal-state) value to `DownloadState`
  and thread it through `CollectionDownloadStatus`
  (`lib/domain/downloads/DownloadCatalog.dart:17-75`) so Downloads and
  system surfaces (notification, etc.) can show it consistently.

## Tests to extend or add

- `test/app/downloads/downloads_cubit_test.dart` — `restart recovery`
  group (~lines 377-410) currently only simulates in-process Cubit
  recreation; needs cases for a scheduler-triggered resume, duplicate
  scheduling, and expired-session-on-resume.
- `test/infrastructure/downloads/http_download_engine_test.dart` —
  already covers Range-resume (~line 154), resuming only onto the same
  source address (~line 188), and resuming across a new session token
  (~line 209); a platform scheduler adapter needs equivalent coverage at
  its own layer (job claim, retry/backoff, cancellation cleanup).
- `test/infrastructure/downloads/drift_download_store_test.dart` — extend
  for any new persisted job/attempt/lease fields and migration.
- `test/infrastructure/downloads/disk_space_storage_probe_test.dart` —
  extend if free-space becomes a hard resume-time gate rather than only
  advisory.
- New: platform scheduler adapter tests (Android/Windows/iOS) for
  process death, restart, duplicate scheduling, network transitions, and
  account/server-removal cleanup of only the targeted jobs and claims.

## Non-goals (per spec)

Everything in the rest of the v0.8.x arc is out of scope here: v0.8.1
automatic playlist download synchronization, v0.8.2 collection smart
synchronization, v0.8.3 storage budgets and reservations, v0.8.4
retention and automatic cleanup, v0.8.5 offline automation hardening.
v0.8.0 is execution durability only — not new sync/budget/retention
policy.

## Likely ADR

Replacing ADR-0020's foreground-only `HttpDownloadEngine` with a
platform-neutral scheduler contract plus Android/Windows/iOS
implementations, and where job/lease/attempt state lives (extended
`TrackDownload`/`DriftDownloadStore` schema vs. a new job table), is a
durable-architecture decision — a candidate for the next free ADR number
(0049 at time of scouting; re-check `docs/adr/` before implementation
since sibling versions scouted in this same batch, e.g. v0.7.1-v0.7.4,
may also claim one).
