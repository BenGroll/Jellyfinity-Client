# Scout: v0.7.4 - Playlist-system hardening

Generated by scouting the repository ahead of implementation. See
`Roadmap to v0.7.md#v074---playlist-system-hardening`. An implementing
agent should still run `python3 tools/agent_context.py v0.7.4` first.

## Goal

Make manual, downloaded, and smart playlists behave as one dependable
curation system at realistic scale — auditing the whole set of playlist
flows together rather than adding a new one, and closing the arc so a
user never needs Jellyfin Web to build or maintain a playlist.

## Current state (confirmed by inspection)

**Dependency:** this version assumes v0.7.1 (artwork), v0.7.2 (smart
rules/preview), and v0.7.3 (smart publication/refresh) have already
landed. As of this scouting pass none of the three is built —
`lib/domain/media/Playlist.dart:11-35` has no smart-rule or artwork-write
fields yet, and `PlaylistRepository` (below) has no smart/artwork
methods. Re-check before starting; if they haven't landed, v0.7.4's scope
that touches them is blocked, not skippable.

**The contract to audit** — `lib/domain/media/PlaylistRepository.dart:1-91`:
`playlists`, `tracks`, `addTracks`, `create`, `rename`, `delete`,
`removeEntries`, `moveEntry`. Two implementations:
- `lib/infrastructure/jellyfin/media/JellyfinPlaylistRepository.dart:1-199`
  (server-backed; every write resolves `MediaId` → local item id first,
  failing closed on a foreign-server id, e.g. `_localIds` at line 190-198).
- `lib/infrastructure/media/CachedPlaylistRepository.dart:1-259` (adds
  cache-then-downloaded-snapshot fallback for reads; writes pass straight
  through with no local invalidation — the comment at lines 203-215
  explains why: a mutation implies the server is reachable, so the
  caller's own reload overwrites the cache).

**Existing gap-handling is already fairly deliberate, not absent:**
- Unreadable/non-track entries: `Page<Track>` carries them as
  `unavailable` (`Partial`, referenced in `PlaylistRepository.tracks` doc
  at lines 24-30) rather than dropping them — numbering stays true to the
  server's playlist.
- Duplicate appearances of the same track: handled by keying removal/move
  on `PlaylistTrack.entryId`, not track id (`lib/domain/media/PlaylistTrack.dart:1-80`,
  esp. lines 7-11, 27-36). Covered by tests: "the same track listed twice
  is two separate rows" (`test/infrastructure/jellyfin/media/jellyfin_playlist_repository_test.dart:132`)
  and "a song listed twice moves the appearance that was dragged"
  (`test/features/music/playlist_reorder_test.dart:73`).
- Missing entry ids (offline/cache/download-snapshot reads, or a row the
  server sent without one): `PlaylistTrack.isEditable` gates this
  (`PlaylistTrack.dart:72-76`); `JellyfinPlaylistRepository.moveEntry`
  refuses a blank entry id explicitly rather than guessing
  (`JellyfinPlaylistRepository.dart:165-172`), tested at
  `jellyfin_playlist_repository_test.dart:259`.
- Reorder against a stale/cached copy: `PlaylistDetailPage` gates
  `canReorder` on `!state.isCached` (`lib/features/music/presentation/detail/PlaylistDetailPage.dart:243-246`);
  `PlaylistTracksCubit.moveEntry` locally reorders optimistically, then
  reloads on success or reverts on failure
  (`lib/features/music/presentation/library/music_collection_cubits.dart:281-333`,
  esp. the revert at line ~330).
- Bulk-add partial availability (v0.7.0/ADR-0048): a checked track no
  longer in `selectableTracks` is silently dropped from the request and
  the dropped count is reported in the result message
  (`lib/features/music/presentation/selection/bulk_playlist_selection.dart:1-82`).
  `addTracks` is **all-or-nothing from the server's point of view** per
  its doc comment (same file, line ~22) — there is no per-track partial
  success on the *write* side, only on the *selection* side. Worth
  re-checking under the hardening pass: what happens today if the server
  rejects one id mid-batch (e.g. one track deleted between selection and
  submit)?

**A genuine unbounded-read gap found:** `DownloadsCubit.reconcilePlaylist`
(`lib/app/downloads/DownloadsCubit.dart:458-489`) loops `while (true)`
paging through **all** of a playlist's tracks with no upper bound before
comparing against the download snapshot (lines 464-477). For a
realistically large playlist (the spec's "realistic scale") this is an
unbounded sequential read on every reconcile (manual refresh, and on
every playlist-opened-online per the doc comment at lines 450-457). This
is the clearest concrete match for the spec's "bound reads... for very
large playlists" requirement — contrast with the existing bounded
pattern below.

**Existing bounded-pagination precedent:** `lib/domain/media/page.dart:1-40`
— `PageRequest.defaultLimit = 100` (line ~21), justified by
`PHILOSOPHY.md` §11 ("no repository ever offers 'give me everything'; a
130k-track library is browsed one window at a time"). Library browsing
honors this window-at-a-time contract throughout
(`lib/infrastructure/jellyfin/media/JellyfinMusicLibraryRepository.dart:532-541`
uses an explicit `pageSize = 200` loop with a real stopping condition).
`ConnectedPlaybackLimits.maxQueueEntries = 1000`
(`lib/domain/connected_playback/ConnectedPlaybackLimits.dart:17-24`) is
the analogous bound already agreed on for handing a queue to another
device — useful precedent for what "bound... for very large playlists"
should look like for playlist mutations/UI, since none currently exists
there.

**Queue-origin / cross-device identity gap:** a playlist-originated queue
only carries the playlist's **name** across a transfer or to a remote
controller, never its id — `originName` on both
`RemotePlaybackSnapshot` (`lib/domain/connected_playback/RemotePlaybackSnapshot.dart:91-95`,
"carried as a name only... does not navigate into the target's listening
context") and `PlaybackTransfer`
(`lib/domain/connected_playback/PlaybackTransfer.dart:71-73`, "a transfer
does not restart the listening context"). This means: (1) a controller
cannot navigate to "Late Night" from another device, by design so far,
and (2) if the playlist is renamed or deleted after the queue started,
the name shown elsewhere goes stale — exactly the "verify identity after
rename... server-side edits" case the spec calls out, and currently
unaddressed for the cross-device path specifically. `QueueOrigin`
(`lib/domain/playback/QueueOrigin.dart:24-43`) itself does carry the real
`playlistId`, so this is a transport-layer narrowing, not a domain gap.

**Download-side identity:** `PlaylistDownload.dart` (`lib/domain/downloads/PlaylistDownload.dart:1-56`)
snapshots membership by position + `MediaId` (not entry id — a download
has nothing to name a live server row with), and
`DownloadedCollection.dart` (`lib/domain/downloads/DownloadedCollection.dart:1-65`)
snapshots the playlist's own name/artwork so it renders offline. Rename,
artwork-change, and account-removal identity all hinge on when these two
snapshots get refreshed — `reconcilePlaylist` refreshes membership
(bounded issue above); nothing surfaced in this pass refreshes
`DownloadedCollection`'s name/artwork on a rename discovered post-hoc
(worth confirming directly — `rg -n "DownloadedCollection" lib/app/downloads`
during implementation).

## Suggested shape (not prescriptive)

Not a new feature — an audit pass structured around the spec's own flow
list (create/rename/delete/add/bulk add/remove/reorder/artwork/smart
refresh/download/queue-origin/cross-device), each checked against: does a
missing-entry-id, unavailable-item, duplicate-appearance, or
partial-server-response case already fail safely (most do — see above),
and is any read/diff/mutation over such a list actually bounded (one
confirmed miss: `reconcilePlaylist`). Android/Windows interaction and
failure-path acceptance and migration/integration/regression coverage
are execution work once the audit above narrows what needs fixing.

## Non-goals (per spec)

Collaborative or cross-user playlist editing is out of scope for the
whole v0.7.x arc. Specific to v0.7.4: nothing here proposes new playlist
capabilities (artwork, smart rules, smart publication belong to
v0.7.1-v0.7.3, which this version depends on rather than re-implements).
This version closes the arc — no new roadmap items should be spun off
from it beyond bug fixes and the coverage listed above.

## Likely ADR

Nothing found in this pass rises to a new durable contract-shape
decision — the existing gap-handling (entry-id keying, `Partial`
unavailable rows, all-or-nothing batch writes) already reflects prior
ADRs (ADR-0024, ADR-0048) and this version's job is auditing and
bug-fixing against them, not replacing them. The one candidate is
**whether to formalize a bound on playlist reconcile/read size** (the
`reconcilePlaylist` unbounded loop) the way `ConnectedPlaybackLimits` and
`PageRequest.defaultLimit` already formalize theirs elsewhere — if that
fix generalizes past a one-off cap, it's a candidate for the next free
ADR number (0049 at time of scouting; re-check `docs/adr/` before
implementation since sibling versions scouted in this batch may also
claim one). A simple bounded-loop fix would not need one.
