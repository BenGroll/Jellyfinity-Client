# Scout: v0.7.2 - Smart playlist rules and preview

Generated by scouting the repository ahead of implementation. This is a
starting brief, not a replacement for `Roadmap to v0.7.md` or `AGENTS.md` —
an implementing agent should still run
`python3 tools/agent_context.py v0.7.2` first.

## Goal

Define an understandable, versioned smart-playlist rule model and a rule
editor with paged preview, so a user can build, save, and preview a smart
playlist without any server playlist being touched yet.

## Current state (confirmed by inspection)

- **No rule/predicate engine exists.** `rg -ni "smart.?playlist|predicate|rule.?engine|RuleGroup"` across `lib` and `test` returns only unrelated Flutter `find.byWidgetPredicate` test matches. This is genuinely new domain, not an extension.
- **No "draft" persistence pattern exists anywhere** (`rg -ni draft lib` is empty) — the "persist drafts separately from active definitions" requirement has no existing convention to reuse; it will need a new shape.
- **Paging precedent is exactly what the preview needs.** `lib/domain/media/page.dart` already defines `PageRequest` (`startIndex`/`limit`, default 100, `.next()`) and `Page<T>` (`content: Partial<T>`, `totalCount`, `source`, `hasMore`) — `lib/domain/media/page.dart:9-39, 63-120`. `PlaylistRepository.playlists`/`.tracks` in `lib/domain/media/PlaylistRepository.dart:18-38` already return `Result<Page<...>>`, so the smart-playlist preview should return the same `Page<Track>` shape.
- **`PageSource` only distinguishes `server` vs `cache`** (`lib/domain/media/page.dart:47-58`) — the spec wants "live, cached, partial, and offline" distinguished. `partial` is already separately modeled via `Partial<T>`/`UnavailableItem` in `lib/core/result/partial.dart:8-24, 36-53` (used for e.g. unreadable playlist entries), but there is no existing `offline` source value — `PageSource` (or an equivalent scoped to preview results) likely needs extending or a preview-specific wrapper.
- **Predicate source data exists and is queryable:**
  - Listening history: `lib/domain/media/ListeningHistoryEntry.dart:14-33` (`context`, `firstPlayedAt`, `lastPlayedAt`, `playCount`), contract at `lib/domain/media/ListeningHistoryRepository.dart:38-46` (`record`, `recent({limit})`). Backing table `ListeningHistoryEntries` (`lib/infrastructure/persistence/database/tables.dart:513-574`) is explicitly **bounded** (`DriftListeningHistoryRepository.maxEntriesPerProfile`, evicts oldest) and **account-scoped** via `accountKey` — matches the spec's "bounded local history" and "account isolation" requirements almost verbatim.
  - Favorites: contract `lib/domain/media/FavoritesRepository.dart:13-24` is write-only (`setFavorite`); favorite state itself arrives attached to `Artist`/`Album`/`Track` reads, or via `CachedFavorites` table (`lib/infrastructure/persistence/database/tables.dart:575-608`, account-scoped, keyed by `(accountKey, itemId)`, has `kind`).
  - Downloads: `TrackDownloads` (`lib/infrastructure/persistence/database/tables.dart:282-353`) and `DownloadOwners` (`:365-393`) are account-scoped and carry denormalized metadata (genres, artists, album) usable as predicate fields even offline.
  - Cached metadata: `CachedMediaItems` (`lib/infrastructure/persistence/database/tables.dart:94-145`) is the general item cache (name, artists, album, track/disc number, duration, year, genre is notably *not* on this table — only on `TrackDownloads.genresJson` — so a genre predicate over the general library may be a live-only field, a real scope distinction the preview must surface).
- **Drift migration precedent is strong and directly reusable.** `AppDatabase.schemaVersion` is currently `11` (`lib/infrastructure/persistence/database/AppDatabase.dart:49`), with `MigrationStrategy.onUpgrade` doing incremental, additive `if (from < N)` steps (`:65` onward) — 10 prior versions of exactly this pattern to follow. Migration tests live in `test/infrastructure/persistence/app_database_migration_test.dart` (one `test(...)` per version bump, e.g. line 256 `'upgrades a v7 database to the v8 favorites cache'`, line 298 for v9→v10). Schema snapshots are frozen per-version under `test/support/drift_schemas/schema_v1.dart` … `schema_v11.dart` plus `schema.dart`, regenerated via `dart run drift_dev schema dump` per the doc comment at `lib/infrastructure/persistence/database/AppDatabase.dart:15-21`.
- **Account scoping is a settled, repo-wide convention**: every profile-scoped table (`TrackDownloads`, `DownloadOwners`, `ListeningHistoryEntries`, `CachedFavorites`, `PendingFavoriteIntents`) uses the same `accountKey` = `"<serverId>/<jellyfinUserId>"` composite, documented at `lib/infrastructure/persistence/database/tables.dart:287-292` and repeated at `:513-521`. A smart-playlist rule/draft table should follow this exact convention for "account isolation."
- **No JSON-rule-blob precedent** in a domain table (closest is `artistsJson`/`genresJson` flattened-array columns on `CachedMediaItems`/`TrackDownloads`, and generic string values on `KeyValueEntries`, `lib/infrastructure/persistence/database/tables.dart:66-78`) — encoding a rule tree (all/any groups, inclusion/exclusion, sort, limit, seed) will likely be a new JSON-in-`TextColumn` design, versioned by a `ruleVersion`/`schemaVersion`-style int column per the spec's own versioning requirement, distinct from but parallel to `AppDatabase.schemaVersion`.

## Suggested shape (not prescriptive)

- A `SmartPlaylistRule`/`RuleGroup` domain model (all/any composition, include/exclude, sort spec, limit, optional deterministic seed for randomization) under `lib/domain/media/`, with a small versioned serializer (`toJson`/`fromJson` + a `ruleModelVersion` field) — not a scripting language, per spec.
- A `SmartPlaylistRepository` contract (mirroring `PlaylistRepository`'s shape) with separate `saveDraft`/`activeDefinitions`/`drafts` accessors so invalid/incompatible/newer-version rows stay stored and recoverable rather than silently dropped or evaluated as empty.
- A Drift table (e.g. `SmartPlaylistDefinitions`) storing `accountKey`, `serverId`, a rule-version int, the serialized rule JSON, a `status` (draft/active), and timestamps — following the `AppDatabase.schemaVersion` 11→12 migration pattern exactly.
- A preview evaluator that, per predicate, decides whether it can be answered live (Jellyfin query), from cache, or not at all offline — returning a `Page<Track>`-shaped result extended with per-rule source/scope labeling, since raw `PageSource` (server/cache) doesn't yet cover "partial"/"offline" as the spec wants them surfaced together.
- A rule editor UI reusing the app's existing paged-list/preview scaffolding (wherever `Page`/`PageRequest` consumers already build paged screens — worth locating one concrete example, e.g. a library browse or search results screen, as the UI precedent) plus validation before save.

## Touchpoints to inspect further

- `lib/domain/media/page.dart` (full file) — whether `PageSource` is the right extension point or a new preview-specific status enum is cleaner.
- `lib/infrastructure/persistence/database/AppDatabase.dart:52-120+` — full `onUpgrade` chain, to see exactly where a v12 step gets appended and what indexes prior versions created for account-scoped tables (e.g. `_listeningHistoryAccountIndex`, `_cachedFavoritesAccountIndex` at `:60-63`) as the index-naming convention to follow.
- `lib/infrastructure/jellyfin/media/JellyfinPlaylistRepository.dart` and `lib/infrastructure/media/CachedPlaylistRepository.dart` — confirm neither currently exposes any query/filter capability beyond `searchTerm` that a "live" rule predicate could reuse against the Jellyfin API.
- `lib/domain/media/ListeningHistoryEntry.dart` (`ListeningContext`/`ListeningContextKind`) and `DriftListeningHistoryRepository.dart` — exact bound (`maxEntriesPerProfile`) and eviction semantics, since rule evaluation over history must respect the same "bounded" contract the spec requires.
- Wherever an existing paged screen (library browse, search) builds its UI from `Page<T>`/`PageRequest` — a concrete widget-level precedent for the "paged preview" UI was not located in this pass and should be searched for directly (e.g. `rg -n "PageRequest" lib/features`).
- `docs/adr/ADR-0025-*listening-history*.md` and `ADR-0028-*favorites*.md` (titles only, don't read in full) — likely have the account-isolation and bounded-history rationale a rule-model ADR would cite rather than re-argue.

## Non-goals (per spec's v0.7.x arc)

Nothing from v0.7.0 (bulk selection, done), v0.7.1 (playlist artwork
management), or v0.7.4 (playlist-system hardening) is in scope. Most
importantly, per the spec's own "Done when" clause: **no server playlist may
be created, mutated, or refreshed by this version** — that is explicitly
v0.7.3's job (smart playlist *publication and refresh*). v0.7.2 only builds,
validates, saves, and previews rule definitions locally.

## Likely ADR

The rule model's versioning/persistence design (draft vs. active storage,
recoverability of invalid/incompatible/newer rule versions, and the
account/server-scoped table shape) is a durable data-model decision and a
candidate for the next free ADR number (0049 at time of scouting; re-check
`docs/adr/` before implementation since sibling versions scouted in this same
batch — v0.7.1, v0.7.3, v0.7.4, v0.8.0 — may also claim one).
