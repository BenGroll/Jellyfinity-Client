# Scout: v0.7.3 - Smart playlist publication and refresh

Generated by scouting the repository ahead of implementation. See
`Roadmap to v0.7.md#v073---smart-playlist-publication-and-refresh` — an
implementing agent should still run `python3 tools/agent_context.py v0.7.3`
first.

## Goal

Turn a saved smart definition into a normal, clearly-marked
Jellyfinity-managed Jellyfin playlist that stays predictably synchronized:
compute the smallest safe add/remove/reorder mutation set on refresh, make
ownership (managed vs. converted-to-manual) explicit, and treat another
client's edits to managed output as a conflict rather than silently
overwriting it.

## Current state (confirmed by inspection)

- **Hard dependency on v0.7.2, which does not exist yet.** A repo-wide
  search for `smart.?playlist|SmartPlaylist|PlaylistDefinition|PlaylistRule`
  across `lib/`, `test/`, and `docs/adr/` returns nothing. There is no
  definition/rule model, no preview, and no "activated definition" concept
  to materialize. This version cannot be implemented in isolation from
  v0.7.2's output shape.
- **Playlist contract has no ownership/managed marker.** `Playlist`
  (`lib/domain/media/Playlist.dart:11-36`) carries only
  `id`/`name`/`itemCount`/`duration`/`availability`/`image` — nothing marks
  a playlist as Jellyfinity-managed or links it back to a source
  definition. `PlaylistRepository`
  (`lib/domain/media/PlaylistRepository.dart:14-91`) is CRUD-shaped:
  `addTracks`, `create`, `rename`, `delete`, `removeEntries`, `moveEntry` —
  all single-shot, caller-driven writes. There is no `publish`/`refresh`/
  `sync` verb and no batched-mutation-set entry point; v0.7.3 will need to
  add to this contract or introduce a sibling one.
- **`moveEntry` takes one absolute index at a time**
  (`lib/domain/media/PlaylistRepository.dart:74-90`,
  `lib/infrastructure/jellyfin/media/JellyfinPlaylistRepository.dart:159-185`)
  — reordering is expressed as a sequence of single-row moves against
  Jellyfin's own index semantics, not a diff/patch. A refresh that computes
  "order changes" will need to translate a target order into a sequence of
  these calls itself; there is no existing order-diff helper.
- **`CachedPlaylistRepository`** (`lib/infrastructure/media/CachedPlaylistRepository.dart`)
  is a read-cache/offline-fallback wrapper only. Writes pass straight
  through to `JellyfinPlaylistRepository` with no cache invalidation
  (`lib/infrastructure/media/CachedPlaylistRepository.dart:203-219` explains
  why: a successful write implies the server is reachable, so the caller's
  reload overwrites the cache). No reconciliation logic lives here.
- **Real precedent for "diff paged inputs, apply smallest mutation set,
  report what changed" exists — but in the opposite direction.**
  `DownloadsCubit.reconcilePlaylist`
  (`lib/app/downloads/DownloadsCubit.dart:458-526`) pages the full server
  playlist, builds `currentIds`/`snapshotIds` sets, computes `added`/
  `removed` (not reorder — order is simply re-recorded from server truth),
  applies only the delta, and returns a `PlaylistDownloadChange` count
  (`lib/domain/downloads/PlaylistDownload.dart:22-54`). This reconciles a
  *local snapshot* to match the *server* (download side); v0.7.3 needs the
  mirror-image direction — reconcile the *server playlist* to match a
  *locally computed target* (definition evaluation output) — but the
  paging/diff/report-counts shape is directly reusable as a pattern.
  `PendingFavoritesSync._reconcile`
  (`lib/app/favorites/PendingFavoritesSync.dart:84-120`) is a second
  precedent: an idempotent, re-entrancy-guarded (`_reconciling` bool) sync
  loop triggered at foreground reconciliation points (offline→online,
  session authenticated), retrying failed items on the next trigger without
  duplicating work — a good shape for "refresh on demand and at safe
  foreground reconciliation points" and for the retry/duplicate-delivery
  test requirement.
- **No "conflict" concept anywhere in `connected_playback`.** A search for
  `conflict` (case-insensitive) across `lib/domain/connected_playback/`
  returns zero hits — there is no existing conflict state machine to reuse
  directly. What *does* exist and is conceptually adjacent:
  - `PlaybackOwnership` (`lib/domain/connected_playback/PlaybackOwnership.dart:20-96`)
    — a scoped owner/controller value with `isLocal`/`isRemote`/
    `ownsLocalQueue`, `claimedBy`/`released` transitions. Same shape as
    "managed output is read-only until converted": one authoritative
    writer, everyone else is a read-only observer of a revisioned
    projection.
  - `CommandOutcome` (`lib/domain/connected_playback/command_outcome.dart:9-72`)
    distinguishes `applied` vs. `duplicate` (idempotent replay, not a
    failure) vs. `stale` (composed against a moved-on revision — resync
    before retrying) vs. `rejected`. This is a strong precedent for the
    "idempotent and resumable" refresh requirement and for distinguishing
    a genuine conflict from a stale-but-retriable state.
  - `StateRevision` (`lib/domain/connected_playback/StateRevision.dart:27-58`)
    — a monotonic revision counter (`Comparable`, `next`, `tryParse`) used
    for optimistic-concurrency style comparisons. Reusable pattern for
    detecting "has the managed playlist been edited since our last known
    revision" without a full diff.
  - `TrackDownload.serverGone` (`lib/domain/downloads/TrackDownload.dart:114,133,154,188`)
    is the closest existing "renamed/deleted output" precedent: a record
    the server no longer lists is marked, not deleted, and un-marked if it
    reappears — same instinct the spec wants for a managed playlist that
    was renamed/deleted server-side.
- **No `isCached`/staleness gate is honored on the download-reconcile
  precedent** (`lib/app/downloads/DownloadsCubit.dart:467-471`): a
  cache-served page is explicitly rejected as a reconciliation source
  ("reconciling against it would treat a stale copy as authoritative").
  Any v0.7.3 refresh reading the managed playlist's current server state
  must apply the same rule — evaluate only against `PageSource.server`
  reads (`lib/domain/media/page.dart:47-104`), never a cached window.

## Suggested shape (not prescriptive)

- A `PublishedPlaylistLink` (or similar) value tying a definition id to a
  `MediaId` playlist id and a managed/manual flag plus a last-known
  server revision/etag — persisted alongside (or inside) whatever v0.7.2
  stores the definition as.
- A diff step, structurally close to `DownloadsCubit.reconcilePlaylist`,
  that pages the definition's current evaluation output and the managed
  playlist's current server tracks, and emits an ordered mutation plan
  (`addTracks` for additions, `removeEntries` for removals,
  `moveEntry` calls for reordering) rather than a wholesale rewrite.
- A conflict check ahead of any refresh: compare the managed playlist's
  last-confirmed state/revision against its current server state; a
  mismatch not explained by Jellyfinity's own last publish is a manual
  edit from elsewhere and should surface as a conflict rather than being
  silently overwritten (`CommandOutcome`'s applied/stale/duplicate
  distinctions are a reasonable vocabulary to borrow).
- Independent state exposure for definition / preview / publication / sync
  per the spec — likely a small state enum or record per managed playlist,
  separate from the definition's own (v0.7.2) preview state.

## Non-goals (per spec)

Scheduling and background download behavior (v0.8.x). Nothing from
v0.7.2's rule/definition authoring or preview UI (upstream dependency, not
this version's scope). Nothing from v0.7.1 (playlist artwork) or v0.7.4
(playlist-system hardening). No collaborative/cross-user playlist editing
(consistent with v0.7.0's stated non-goals for the same domain).

## Likely ADR

The managed/manual ownership model — "managed output is read-only in
Jellyfinity until the user converts it to a manual playlist; manual edits
from another client are reported as a conflict before replacement" — is a
durable contract decision on `PlaylistRepository`, a shared, cross-version
repository. It is a candidate for the next free ADR number (0049 at time
of scouting; re-check `docs/adr/` before implementation, since sibling
versions v0.7.1/v0.7.2/v0.7.4/v0.8.0 are being scouted in this same batch
and may also claim one). The diff/mutation-set algorithm itself (how
additions, removals, and reorders are computed and sequenced against
Jellyfin's single-index `moveEntry`) is a second, smaller candidate if it
turns out non-obvious in practice.
